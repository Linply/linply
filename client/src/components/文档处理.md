处理链路分为“浏览器上传”和“后台入库索引”两段。`KnowledgeDocuments.tsx` 负责前一段，并通过轮询展示后一段的状态。

**1. 用户选择文件并校验**

`handleUpload` 先检查：

- 文件是否存在
- 扩展名是否为 `.md`、`.markdown`、`.csv`
- 文件是否为空

不符合时直接提示，不创建文档记录。见 [KnowledgeDocuments.tsx](/Users/pc/Documents/customer_service_agent/client/src/components/KnowledgeDocuments.tsx:204)。

**2. 判断走哪种上传路径**

前端先查询服务端能力：

- 已配置对象存储和 Redis 队列：走分片上传与后台 Worker
- 任一未配置：走旧的直接上传路径，浏览器把完整文件读成文本，再通过接口提交

生产环境通常走第一种。判断逻辑在 [routers.ts](/Users/pc/Documents/customer_service_agent/server/routers.ts:459)。

**3. 创建分片上传会话**

服务端会：

1. 按文件大小计算分片大小。
2. 在 `knowledge_documents` 创建一条文档记录，状态为 `uploading`。
3. 在对象存储创建 multipart upload，得到 `objectKey` 和 `uploadId`。
4. 返回 `documentId`、分片大小、总片数。

前端把这些续传必要信息保存到 `localStorage`。下次选择同一文件时，会先检查此会话和已上传分片，能够从中断处继续。见 [KnowledgeDocuments.tsx](/Users/pc/Documents/customer_service_agent/client/src/components/KnowledgeDocuments.tsx:220) 和 [routers.ts](/Users/pc/Documents/customer_service_agent/server/routers.ts:489)。

**4. 浏览器分批并发上传分片**

前端先从对象存储读取已上传的分片编号，再找出剩余分片。

对于剩余分片：

1. 每次最多向后端申请 20 个预签名 URL。
2. 每个 URL 对应一个分片编号。
3. 用 `file.slice(...)` 从浏览器文件中切出该分片。
4. 用 `PUT` 直接上传到对象存储。
5. 同一时刻最多上传 `UPLOAD_CONCURRENCY = 3` 个分片。
6. 上传进度 = 已完成字节数 + 当前并发分片已上传字节数，再除以文件总大小。

20 个传完，再申请下一组 20 个 URL，直到传完。见 [KnowledgeDocuments.tsx](/Users/pc/Documents/customer_service_agent/client/src/components/KnowledgeDocuments.tsx:259)。

**5. 服务端校验并完成对象存储文件**

浏览器调用 `completeUpload` 后，服务端会校验：

- 分片编号是否连续，从 1 开始
- 分片数量是否等于预期数量
- 已上传字节总数是否等于原文件大小

通过后，服务端调用对象存储的 Complete Multipart Upload 将分片合并成一个文件。随后状态短暂更新为 `uploaded`，再向 `knowledge-parse` 队列投递解析任务，并改为 `parse_queued`。见 [routers.ts](/Users/pc/Documents/customer_service_agent/server/routers.ts:620)。

**6. 解析 Worker 读取并拆分文件**

知识库 Worker 从 `knowledge-parse` 队列取到任务后：

1. 检查任务携带的 `uploadVersion` 是否仍是当前版本，过期任务不处理。
2. 清理此文档先前生成的知识条目。
3. 状态改为 `parsing`，进度归零。
4. 从对象存储以流形式读取文件。
5. CSV 按表头 `title, content, category, keywords` 解析；Markdown 按标题段落拆成知识条目。
6. 每累计 100 条，批量写入 `knowledge_base`，其向量状态初始为 `pending`。
7. 每写完一批就更新 `parsedChunks` 和 `totalChunks`。

读取流式文件避免一次将整个文件读进 Worker 内存。核心处理在 [ingest.ts](/Users/pc/Documents/customer_service_agent/server/knowledge/ingest.ts:135)。

**7. 投递向量生成任务**

每个 100 条知识条目的批次写入数据库后，解析 Worker 会立刻把这一批的条目 ID 投给 `knowledge-embed` 队列。

向量 Worker 收到后，对每条知识：

1. 组合标题、正文等内容形成 embedding 输入。
2. 调用 embedding 服务生成向量。
3. 将向量写回 `knowledge_base`。
4. 检查是否与现有条目冲突，并标记可能冲突项。
5. 当全部条目都成功或失败后，更新文档最终状态。

只要不是所有条目都生成向量失败，最终状态为 `completed`；全部失败则是 `failed`，并记录 `failureStage: "embedding"`。见 [ingest.ts](/Users/pc/Documents/customer_service_agent/server/knowledge/ingest.ts:80)。

**8. 前端轮询结果**

页面发现存在处理中状态时，会每 1.5 秒重新请求文档列表，更新“等待解析 / 解析中 / 索引中 / 已完成 / 失败”等显示。见 [KnowledgeDocuments.tsx](/Users/pc/Documents/customer_service_agent/client/src/components/KnowledgeDocuments.tsx:171)。

当前实现的实际状态主路径为：

```text
uploading
  -> uploaded
  -> parse_queued
  -> parsing
  -> indexing
  -> completed / failed
```

需要注意：`embed_queued` 已定义、前端也能显示，但当前 Worker 代码在解析时投递向量任务后，并没有将文档状态明确写成 `embed_queued`，而是在解析结束后直接改为 `indexing`。因此这个状态目前没有出现在这条实际主流程中。
